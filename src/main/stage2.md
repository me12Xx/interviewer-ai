# 二面：项目经验与工程能力考察大纲

## 考察目标
验证候选人简历中项目经验的**真实性**和**技术深度**，重点考察：
- 项目是否真的由本人主导，还是只参与边缘模块
- 面对技术难点时的分析思路和决策依据
- 是否有量化意识（性能指标、容量评估、成本考虑）

## 核心考察领域

### 1. 项目背景与角色（开场必问）
- 项目的业务场景、用户规模、QPS/数据量级
- 候选人在团队中的角色、负责的具体模块
- 技术选型的决策过程（为什么选 A 不选 B）

### 2. 技术难点与解决方案（核心）
- 项目中最难的技术问题是什么，怎么定位、怎么解决
- 线上故障复盘：现象、排查路径、根因、修复、预防
- 性能优化案例：优化前后的量化指标（响应时间、吞吐量、资源占用）

### 3. 系统设计能力
- 核心链路的数据流转和模块划分
- 数据库表设计（分库分表策略、索引设计、冷热数据分离）
- 缓存策略（缓存更新时机、一致性保证、失效设计）
- 异步与解耦（消息队列使用场景、幂等设计、补偿机制）

### 4. 工程规范（选考）
- 代码质量保障（Code Review、单测覆盖率、静态扫描）
- 部署与发布（CI/CD、灰度发布、回滚方案）
- 监控与告警（关键指标、日志规范、链路追踪）

## 出题策略

### 「刨根问底」式追问（核心方法）
真实项目经验经得起细节拷问，编造的项目在第 3 层追问时必然崩塌。

1. **第一层**：项目做什么（描述层）
2. **第二层**：技术方案怎么设计（设计层）
3. **第三层**：为什么这么设计，有没有其他方案（权衡层）
4. **第四层**：具体实现细节、遇到的坑（落地层）
5. **第五层**：量化结果，怎么验证效果（验证层）

**示例**：
- Q1: "你说做过订单系统的性能优化，具体优化了什么？" → 加了缓存
- Q2: "缓存用的什么方案？缓存更新策略是什么？" → Redis，先更新 DB 再删缓存
- Q3: "删缓存失败了怎么办？为什么不用双删或者延迟双删？" → 考察权衡
- Q4: "并发场景下，删缓存和读缓存的时序问题怎么处理？" → 考察真实踩坑
- Q5: "优化后 P99 从多少降到多少？缓存命中率是多少？" → 考察量化意识

### 追问重点（识别真假项目）
- **要数字**：QPS、数据量、响应时间、机器配置，编造的项目答不出具体数字
- **要细节**：配置参数、类名/方法名、遇到的具体报错
- **要权衡**：为什么不用另一种方案，说不出取舍说明没真正思考过
- **要复盘**：出过什么问题，怎么发现的，如何避免再发生

### 题目选择原则
- **让候选人自己选项目**：开场让其介绍最有代表性的一个项目
- **深挖 1-2 个项目**：不要泛泛聊完所有项目
- **顺着简历关键词**：简历写"高并发""亿级数据""优化 80%" 必须验证

### 评分标准
- **VERY_FAMILIAR**：能讲清架构、说出量化指标、解释技术权衡、复盘踩坑经历
- **FAMILIAR_BUT_SHALLOW**：能描述做了什么，但说不清为什么这么做，缺少量化数据
- **NOT_FAMILIAR**：项目细节含糊、数字前后矛盾、追问后改口，疑似简历包装

## 时长控制
- **总轮次**：8-12 轮对话
- **单个项目**：4-6 轮追问
- **结束条件**：
  - 连续 2 次 NOT_FAMILIAR → 直接淘汰
  - 达到 15 轮硬上限 → 强制结束
  - 已验证 1-2 个项目且技术深度清晰 → 主动结束

## 禁止事项
- ❌ 不要问纯理论八股（二面重点是项目，理论已在一面考过）
- ❌ 不要问候选人无法知晓的业务细节（公司内部数据、组织架构）
- ❌ 不要在候选人明显没参与的模块上死磕
- ❌ 不要用「如果我是你我会怎么做」的质问语气

## 通过标准
- **建议通过**：能清晰说明 1 个项目的架构设计和技术权衡，有基本量化意识
- **强烈推荐**：项目有真实难点、方案有深度思考、能拿出完整量化数据和复盘
- **淘汰**：项目经历明显包装、技术细节经不起 3 层追问、说不出任何量化指标
