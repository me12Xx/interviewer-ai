## Redis简介

Redis是一个开源的高性能键值对数据库，全称是Remote Dictionary Server。Redis将数据存储在内存中，因此读写速度非常快，常被用作缓存、消息队列和分布式锁等场景。

Redis支持多种数据类型，包括字符串String、列表List、集合Set、有序集合Sorted Set、哈希Hash等。Redis还支持位图Bitmap、HyperLogLog、地理空间Geo、流Stream等高级数据结构。

Redis的主要特点包括：数据存储在内存中，读写速度极快，官方数据显示读的速度可达11万次每秒，写的速度可达8万次每秒。支持数据持久化，可以将内存中的数据保存到磁盘，重启后可以再次加载使用。支持多种数据构，不仅仅是简单的键值对。支持主从复制，提供高可用性。支持事务，可以将多个命令打包执行。支持发布订阅模式，可以实现消息通信。

Redis是单线程模型，但通过IO多路复用技术实现了高并发。Redis 6.0之后引入了多线程，但只用于处理网络IO，核心的命令执行仍然是单线程。单线程的好处是避免了线程切换和竞态条件，简化了实现，保证了操作的原子性。

## Redis的五种基本数据类型

Redis的字符串String是最基本的数据类型，可以存储字符串、整数或浮点数。字符串的最大长度是512MB。常用命令包括SET、GET、INCR、DECR、APPEND等。字符串类型的应用场景包括缓存、计数器、分布式锁等。

Redis的列表List是一个双向链表，可以从两端插入和删除元素。列表中的元素是有序的，可以重复。常用命令包括LPUSH、RPUSH、LPOP、RPOP、LRANGE等。列表类型的应用场景包括消息队列、时间线、最新消息等。

Redis的集合Set是一个无序的字符串集合，集合中的元素是唯一的，不允许重复。常用命令包括SADD、SREM、SMEMBERS、SISMEMBER、SINTER、SUNION、SDIFF等。集合类型的应用场景包括标签系统、好友关系、共同关注等。

Redis的有序集合Sorted Set也叫ZSet，是在集合的基础上为每个元素关联一个分数score，元素按照分数从小到大排序。有序集合中的元素是唯一的，但分数可以重复。常用命令包括ZADD、ZREM、ZSCORE、ZRANGE、ZREVRANGE、ZRANGEBYSCORE等。有序集合的应用场景包括排行榜、优先级队列、延时队列等。

Redis的哈希Hash是一个键值对集合，适合存储对象。哈希中的每个键值对称为一个field-value对。常用命令包括HSET、HGET、HMSET、HMGET、HGETALL、HDEL等。哈希类型的应用场景包括存储用户信息、商品信息等结构化数据。

## Redis的持久化机制

Redis提供了RDB和AOF两种持久化机制，可以将内存中的数据保存到磁盘，防止数据丢失。

RDB即Redis Database是Redis的默认持久化方式，通过快照snapshot的方式将某个时间点的内存数据保存到磁盘。RDB会生成一个dump.rdb文件，该文件是一个经过压缩的二进制文件，通过该文件可以还原数据。

RDB持久化的触发方式包括：手动执行SAVE或BGSAVE命令。满足配置文件中的save规则，例如save 900 1表示900秒内至少有1个键被修改则触发。执行FLUSHALL命令清空所有数据。执行主从复制时，主节点会自动生成RDB文件。

SAVE命令会阻塞Redis服务器进程，直到RDB文件创建完毕，期间Redis不能处理任何命令请求。BGSAVE命令会创建一个子进程来生成RDB文件，主进程继续处理命令请求，不会阻塞。

RDB的优点是：RDB文件是一个紧凑的二进制文件，适合用于备份和灾难恢复。RDB恢复数据的速度比AOF快。RDB对Redis的性能影响较小，因为持久化工作由子进程完成。RDB的缺点是：可能会丢失最后一次快照之后的数据，无法做到实时持久化。生成快照时需要fork子进程，如果数据量很大，fork过程会比较耗时，可能导致Redis暂停服务。

AOF即Append Only File持久化通过记录Redis服务器执行的所有写操作命令来实现持久化。AOF文件是一个文本文件，记录了所有的写命令，通过重新执行这些命令可以还原数据。

AOF持久化的同步策略有三种：always表示每次写操作都立即同步到AOF文件，数据最安全但性能最差。everysec表示每秒同步一次，是默认策略，兼顾了性能和数据安全。no表示由操作系统决定何时同步，性能最好但可能丢失较多数据。

AOF文件会随着写操作的增加而不断增大，Redis提供了AOF重写机制来压缩AOF文件。AOF重写不是直接修改现有的AOF文件，而是读取Redis中的数据，生成一个新的AOF文件，用更简洁的命令表示相同的数据状态。可以通过BGREWRITEAOF命令手动触发AOF重写，也可以通过配置自动触发。

AOF的优点是：数据更安全，可以配置为每秒同步一次，最多丢失1秒的数据。AOF文件是文本文件，易于理解和修改。AOF的缺点是：AOF文件通常比RDB文件大。AOF的恢复速度比RDB慢。如果同步策略设置不当，AOF会影响性能。

## Redis的过期策略

Redis的过期策略用于处理设置了过期时间的键，当键过期后需要从内存中删除。Redis采用惰性删除和定期删除两种策略结合的方式。

惰性删除lazy expiration是指当访问一个键时，检查该键是否过期，如果过期则删除。惰性删除的优点是对CPU友好，只在访问键时才检查过期，不会占用额外的CPU时间。缺点是对内存不友好，如果一个键已经过期但一直没有被访问，它会一直占用内存，造成内存浪费。

定期删除periodic expiration是指Redis会定期随机检查一部分设置了过期时间的键，如果发现过期则删除。Redis默认每秒执行10次过期检查，每次随机检查20个键，如果过期键的比例超过25%，则继续检查，直到过期键的比例降到25%以下或者检查时间超过限制。

定期删除是一种主动清理机制，可以及时释放内存，但如果过期键太多，可能影响Redis的性能。惰性删除是一种被动清理机制，对性能影响小，但可能造成内存浪费。两种策略结合使用，可以在性能和内存之间取得平衡。

如果过期键太多，定期删除和惰性删除都来不及清理，内存占用会持续增加。此时需要依赖Redis的内存淘汰策略来释放内存。

## Redis的内存淘汰策略

当Redis内存使用达到maxmemory限制时，会触发内存淘汰策略，删除一些键来释放内存。Redis提供了多种内存淘汰策略，可以通过maxmemory-policy配置。

noeviction是默认策略，不淘汰任何键，当内存不足时，新写入操作会返回错误，但不影响读操作。这种策略适合Redis仅作为缓存且不能丢失数据的场景。

allkeys-lru从所有键中使用LRU算法淘汰最近最少使用的键。LRU即Least Recently Used，优先淘汰最长时间没有被访问的键。这是最常用的淘汰策略，适合大部分场景。

allkeys-random从所有键中随机淘汰键。这种策略适合所有键的访问概率差不多的场景。

volatile-lru从设置了过期时间的键中使用LRU算法淘汰。如果没有键设置过期时间，则等同于noeviction。这种策略适合部分键不能被淘汰的场景。

volatile-random从设置了过期时间的键中随机淘汰。如果没有键设置过期时间，则等同于noeviction。

volatile-ttl从设置了过期时间的键中淘汰即将过期的键，即选择TTL最小的键淘汰。这种策略根据过期时间来淘汰，适合有明确过期优先级的场景。

allkeys-lfu从所有键中使用LFU算法淘汰最不经常使用的键。LFU即Least Frequently Used，优先淘汰访问频率最低的键。LFU比LRU更能反映键的热度。

volatile-lfu从设置了过期时间的键中使用LFU算法淘汰。

选择淘汰策略时，如果数据有明显的冷热区分，推荐使用allkeys-lru或allkeys-lfu。如果所有键的重要性相同，可以使用allkeys-random。如果应用对某些键有明确的过期时间要求，可以使用volatile-ttl。

## Redis的事务

Redis的事务提供了一种将多个命令打包执行的机制。Redis事务通过MULTI、EXEC、DISCARD和WATCH四个命令实现。

MULTI命令用于开启事务，之后的所有命令都会被放入队列中缓存起来，不会立即执行。EXEC命令用于执行事务，会按照命令的顺序依次执行队列中的所有命令。DISCARD命令用于取消事务，清空命令队列并退出事务模式。

Redis事务的执行过程：客户端发送MULTI命令开启事务。客户端发送一系列命令，这些命令会被放入队列中。客户端发送EXEC命令，Redis按顺序执行队列中的所有命令。如果在EXEC之前发送DISCARD命令，则取消事务，清空队列。

WATCH命令用于实现乐观锁，可以监视一个或多个键，如果在事务执行之前这些键被其他客户端修改，事务将被打断，EXEC命令返回空值。WATCH命令必须在MULTI之前执行。UNWATCH命令用于取消对所有键的监视。

Redis事务的特点：Redis事务中的所有命令都会按顺序执行，不会被其他客户端的命令插入。Redis事务是原子性的，要么全部执行，要么全部不执行。但这里的原子性与传统数据库不同，Redis事务不支持回滚，如果事务中某个命令执行失败，其他命令仍然会继续执行。

Redis事务不支持回滚的原因是：Redis命令只会因为语法错误而失败，或者对错误类型的键执行操作，这些问题应该在开发阶段被发现，生产环境不应该出现。不支持回滚可以保持Redis的简单和高性能。

如果在执行EXEC之前发现命令语法错误，Redis会拒绝执行整个事务。如果在执行EXEC后某个命令执行失败，Redis不会回滚已经执行的命令，会继续执行后续的命令。

## Redis的主从复制

Redis的主从复制replication功能可以将主节点master的数据复制到从节点slave，实现数据的备份和读写分离。主从复制是Redis高可用的基础。

主从复制的工作原理：从节点向主节点发送SYNC或PSYNC命令请求同步数据。主节点执行BGSAVE命令生成RDB文件，同时将新的写命令缓存到缓冲区。主节点将RDB文件发送给从节点，从节点加载RDB文件恢复数据。主节点将缓冲区中的写命令发送给从节点，从节点执行这些命令。之后主节点会持续将写命令发送给从节点，从节点执行命令保持数据同步。

Redis 2.8之前使用SYNC命令进行全量同步，效率较低。Redis 2.8之后引入了PSYNC命令，支持部分同步。当从节点断开重连后，如果主节点的复制积压缓冲区中还保存着断开期间的写命令，只需要将这些命令发送给从节点即可，无需全量同步。

主从复制的配置方式：在从节点的配置文件中添加slaveof或replicaof配置项，指定主节点的IP和端口。或者在从节点启动后执行SLAVEOF或REPLICAOF命令动态配置主从关系。Redis 5.0之后，SLAVEOF命令被REPLICAOF命令替代，但SLAVEOF仍然可用。

主从复制的优点：实现了数据的热备份，提高了数据的可靠性。可以实现读写分离，主节点负责写操作，从节点负责读操作，提高了系统的并发能力。主从复制的缺点：主节点故障后需要手动将从节点升级为主节点。写操作无法负载均衡，所有写操作都在主节点。存在数据延迟，从节点的数据可能落后于主节点。

## Redis哨兵模式

Redis哨兵Sentinel是Redis的高可用解决方案，可以自动监控主从节点的状态，当主节点故障时自动将从节点升级为主节点，实现故障自动转移。

哨兵的主要功能包括：监控monitoring，哨兵会定期检查主节点和从节点是否正常工作。通知notification，当某个Redis节点出现故障时，哨兵可以通过API通知系统管理员或其他应用程序。故障转移failover，当主节点故障时，哨兵会自动将一个从节点升级为主节点，并让其他从节点改为复制新的主节点。配置提供configuration provider，客户端连接哨兵获取当前的主节点地址。

哨兵的工作原理：哨兵通过发送PING命令检测主节点和从节点的状态。如果节点在指定时间内没有回复或回复错误，哨兵会将该节点标记为主观下线。当多个哨兵都认为主节点主观下线时，会进行投票，如果投票数达到配置的阈值，主节点被标记为客观下线。哨兵开始故障转移流程，选举出一个领头哨兵负责执故障转移。领头哨兵从从节点中选择一个作为新的主节点，选择的依据包括从节点的优先级、复制偏移量、运行ID等。领头哨兵向被选中的从节点发送SLAVEOF NO ONE命令，使其升级为主节点。领头哨兵向其他从节点发送SLAVEOF命令，让它们复制新的主节点。哨兵会将原来的主节点标记为从节点，当它恢复后会自动成为新主节点的从节点。

哨兵模式通常需要配置多个哨兵节点，形成哨兵集群，提高可靠性。哨兵集群中的节点会相互通信，共同监控Redis节点。建议至少配置3个哨兵节点，并且哨兵节点数量应该是奇数，便于在选举时达成多数。

## Redis集群

Redis Cluster是Redis的分布式解决方案，将数据分散存储在多个节点上，实现了数据的分片和高可用。Redis Cluster不需要哨兵，集群节点之间会相互通信，自动进行故障转移。

Redis Cluster采用哈希槽hash slot来分配数据。Redis Cluster将整个数据集划分为16384个哈希槽，每个节点负责一部分哈希槽。当存储一个键值对时，先对键进行CRC16哈希运算，然后对16384取模，得到该键所属的哈希槽，再根据槽的分配找到对应的节点进行存储。

Redis Cluster的工作原理：集群中的每个节点都保存了哈希槽的分配信息和其他节点的信息。节点之间通过Gossip协议交换信息，包括节点的状态、哈希槽的分配等。客户端可以连接集群中的任意节点，如果访问的键不在该节点，节点会返回MOVED错误和正确的节点地址，客户端重定向到正确的节点。

Redis Cluster支持主从复制，每个主节点可以有多个从节点。当主节点故障时，集群会自动将其中一个从节点升级为主节点，实现故障自动转移。集群中的节点通过心跳机制检测其他节点的状态，当半数以上的主节点认为某个主节点下线时，该节点被标记为下线，其从节点会被升级为主节点。

Redis Cluster的优点：实现了数据的自动分片，突破了单机内存限制。实现了高可用，支持故障自动转移。客户端可以连接任意节点，使用方便。Redis Cluster的缺点：不支持多键操作，如果多个键不在同一个节点，操作会失败。不支持多数据库，只能使用数据库0。集群的搭建和维护比较复杂。

## Redis的应用场景

缓存是Redis最常见的应用场景。将热点数据缓存在Redis中，可以大幅减轻数据库的压力，提高系统的响应速度。缓存的更新策略包括：缓存穿透、缓存击穿、缓存雪崩等问题需要特别注意。

分布式锁可以使用Redis的SETNX命令实现。SETNX命令在键不存在时设置值并返回1，键已存在时不设置并返回0，可以用来实现互斥。为了防止死锁，设置锁时应该同时设置过期时间。释放锁时需要判断锁是否是自己持有的，避免误删其他客户端的锁。

消息队列可以使用Redis的列表或Stream实现。列表的LPUSH和RPOP命令可以实现简单的消息队列。Stream是Redis 5.0引入的新数据结构，专门用于消息队列，支持消息的持久化、消费组、消息确认等高级功能。

排行榜可以使用有序集合实现。有序集合的ZADD命令可以添加成员和分数，ZREVRANGE命令可以按分数从高到低获取排名，ZRANK命令可以获取成员的排名。

计数器可以使用字符串的INCR命令实现。INCR命令是原子操作，可以保证并发环境下计数的准确性。常见的应用包括文章浏览量、视频播放次数、接口限流等。

会话缓存可以将用户的Session信息存储在Redis中，实现Session共享。在分布式系统中，多个应用服务器可以共享Redis中的Session，解决了Session不一致的问题。
