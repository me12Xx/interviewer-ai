## Java内存模型JMM

Java内存模型JMM定义了Java虚拟机在计算机内存中的工作方式。JMM的主要目标是定义程序中各种变量的访问规则，即关注在虚拟机中把变量值存储到内存和从内存中取出变量值这样的底层细节。

JMM规定所有的变量都存储在主内存中，每个线程还有自己的工作内存。线程的工作内存中保存了被该线程使用的变量的主内存副本。线程对变量的所有操作都必须在工作内存中进行，而不能直接读写主内存中的数据。不同线程之间也无法直接访问对方工作内存中的变量，线程间变量值的传递均需要通过主内存来完成。

JMM通过控制主内存与每个线程的工作内存之间的交互，来提供内存可见性保证。JMM定义了八种原子操作来完成主内存与工作内存之间的交互：lock、unlock、read、load、use、assign、store、write。

JMM的三大特性是原子性、可见性和有序性。原子性指操作不可中断，要么全部执行成功要么全部不执行。可见性指一个线程修改了共享变量的值，其他线程能够立即看到修改后的值。有序性指程序执行的顺序按照代码的先后顺序执行。

JMM通过happens-before原则来保证多线程程序的正确性。happens-before规则包括：程序顺序规则、锁定规则、volatile变量规则、线程启动规则、线程终止规则、线程中断规则、对象终结规则、传递性规则。

## volatile的可见性保证

volatile关键字可以保证变量的可见性。当一个变量被声明为volatile后，对这个变量的写操作会立即刷新到主内存，对这个变量的读操作会从主内存中读取最新的值。

volatile的可见性是通过内存屏障实现的。写入volatile变量时，JMM会在写操作后插入一个StoreLoad屏障，强制将该变量的最新值刷新到主内存。读取volatile变量时，JMM会在读操作前插入一个LoadLoad屏障和LoadStore屏障，强制从主内存中读取最新值。

volatile变量的写操作happens-before后续对该变量的读操作。这意味着如果线程A写入了一个volatile变量，线程B随后读取了同一个volatile变量，那么线程A在写入volatile变量之前所做的所有修改对线程B都是可见的。

需要注意的是，volatile不能保证复合操作的原子性。例如i加加操作包括读取i的值、对i加1、将新值写回这三个步骤，volatile只能保证每个步骤的可见性，但不能保证三个步骤作为整体的原子性。

volatile适合用作状态标志位，例如一个线程修改标志位通知其他线程停止工作。volatile也适合用于单次赋值的场景，只要不涉及依赖当前值的复合操作，就可以安全地使用volatile。

## volatile禁止指令重排序

volatile关键字除了保证可见性，还能禁止指令重排序。指令重排序是指编译器或处理器为了优化程序性能而对指令执行顺序进行调整的一种手段。

指令重排序在单线程环境下不会影响程序的正确性，但在多线程环境下可能导致程序出现非预期的行为。volatile通过插入内存屏障来禁止特定类型的指令重排序。

volatile写操作的内存屏障策略：在每个volatile写操作前面插入一个StoreStore屏障，防止volatile写与前面的普通写重排序。在每个volatile写操作后面插入一个StoreLoad屏障，防止volatile写与后面的volatile读写重排序。

volatile读操作的内存屏障策略：在每个volatile读操作后面插入一个LoadLoad屏障和LoadStore屏障，防止volatile读与后面的普通读和普通写重排序。

内存屏障分为四种类型：LoadLoad屏障保证Load1的读取操作在Load2之前完成，StoreStore屏障保证Store1的写入操作在Store2之前完成，LoadStore屏障保证Load1的读取操作在Store2之前完成，StoreLoad屏障保证Store1的写入操作在Load2之前完成。其中StoreLoad屏障的开销最大，也被称为全能屏障。

## DCL单例为什么要volatile

双重检查锁单例模式中，实例变量必须用volatile修饰，否则可能出现线程安全问题。单例模式的双重检查锁代码中，创建对象的语句uniqueInstance等于new Singleton()实际上包含三个步骤：为对象分配内存空间、初始化对象、将引用指向分配的内存地址。

由于指令重排序的存在，这三个步骤的执行顺序可能变为：分配内存、将引用指向内存、初始化对象。如果线程A执行到第二步时被暂停，此时对象还没有初始化完成，但引用已经不为null了。此时线程B执行getInstance方法，第一次检查发现实例不为null，直接返回这个未初始化完成的实例，使用时就会出错。

使用volatile修饰实例变量后，volatile会在写操作前插入StoreStore屏障，确保对象的初始化操作happens-before引用赋值操作，从而禁止了这两个步骤的重排序。这样就保证了当其他线程看到实例不为null时，该实例一定已经初始化完成。

从内存屏障的角度理解，volatile写操作前的StoreStore屏障保证了内存分配和对象初始化这两个写操作在引用赋值这个写操作之前完成。volatile写操作后的StoreLoad屏障则保证了引用赋值对后续的读操作可见。

## happens-before原则

happens-before原则是JMM中判断数据是否存在竞争、线程是否安全的重要依据。如果操作A happens-before操作B，那么操作A产生的影响对操作B可见。

程序顺序规则：在一个线程内，按照代码的顺序，前面的操作happens-before后面的操作。注意这里是控制流顺序而不是程序代码顺序，因为可能存在分支和循环。

锁定规则：一个unlock操作happens-before后面对同一个锁的lock操作。也就是说，如果线程A释放了锁M，随后线程B获取了锁M，那么线程A在释放锁之前的所有操作对线程B获取锁之后都是可见的。

volatile变量规则：对一个volatile变量的写操作happens-before后续对该变量的读操作。这保证了volatile变量的可见性和有序性。

线程启动规则：Thread对象的start方法happens-before此线程的每一个动作。也就是说，主线程启动子线程之前的所有操作对子线程都是可见的。

线程终止规则：线程中的所有操作都happens-before其他线程检测到该线程已经终止。通过Thread.join方法或Thread.isAlive的返回值可以检测线程是否终止。

线程中断规则：对线程interrupt方法的调用happens-before被中断线程检测到中断事件的发生。可以通过Thread.interrupted方法检测是否有中断发生。

对象终结规则：一个对象的初始化完成happens-before它的finalize方法的开始。

传递性规则：如果操作A happens-before操作B，操作B happens-before操作C，那么操作A happens-before操作C。

## volatile不保证原子性

volatile关键字能保证变量的可见性，但不能保证对变量的操作是原子性的。最典型的例子就是自增操作i加加，虽然i声明为volatile，但多线程并发执行i加加仍然会出现线程安全问题。

i加加操作实际上包含三个步骤：读取i的值、对i加1、将新值写回i。volatile只能保证每个步骤的可见性，但不能保证三个步骤作为一个整体的原子性。

多线程并发执行i加加时可能出现这种情况：线程A读取i的值为5，线程B也读取i的值为5，然后线程A将i加1得到6并写回，线程B也将i加1得到6并写回。两个线程都执行了一次加1操作，但最终i的值只增加了1而不是2。

如果要保证i加加操作的线程安全，可以使用synchronized关键字、Lock锁或者AtomicInteger原子类。synchronized和Lock通过加锁保证同一时刻只有一个线程执行i加加操作。AtomicInteger使用CAS操作保证原子性，性能优于加锁方式。

volatile适用的场景是：对变量的写操作不依赖当前值，或者能确保只有单个线程更新变量的值。常见的应用场景是状态标志位，一个线程负责修改标志位，其他线程只读取标志位。

## 乐观锁与悲观锁

悲观锁总是假设最坏的情况，认为共享资源每次被访问时都会出现问题，所以每次在获取资源操作时都会上锁，其他线程想拿到这个资源就会阻塞。Java中synchronized和ReentrantLock等独占锁就是悲观锁思想的实现。

悲观锁的优点是能够确保数据的一致性，适合写操作频繁的场景。缺点是在高并发场景下，激烈的锁竞争会造成线程阻塞，大量阻塞线程会导致频繁的上下文切换，增加系统开销。悲观锁还可能出现死锁问题。

乐观锁总是假设最好的情况，认为共享资源每次被访问时不会出现问题，线程可以不停地执行，无需加锁也无需等待，只是在提交修改时验证对应的资源是否被其他线程修改了。乐观锁一般通过版本号机制或CAS算法实现。

乐观锁的优点是不存在锁竞争和死锁问题，在并发冲突较少的情况下性能很好。缺点是如果冲突频繁发生，会导致大量的失败重试，反而影响性能，甚至导致CPU飙升。

版本号机制是在数据表中增加一个version字段，每次更新数据时version加1。更新数据时，先读取version值，提交更新时判断version是否与读取时相同，如果相同则更新成功，否则重试。

CAS机制是比较并交换，包含三个操作数：内存位置V、预期原值E、新值N。当且仅当V的值等于E时，才会用N更新V的值，否则什么都不做。CAS是一条CPU原子指令，由硬件保证原子性。

## CAS算法原理

CAS的全称是Compare And Swap，即比较并交换。CAS涉及三个操作数：要更新的变量值V、预期值E、拟写入的新值N。当且仅当V的值等于E时，CAS通过原子方式用新值N来更新V的值。如果不等，说明已经有其他线程更新了V，则当前线程放弃更新。

CAS是一个原子操作，底层依赖于一条CPU的原子指令。不同架构的处理器实现方式不同，x86架构下使用cmpxchg指令，ARM架构下使用ldrex和strex指令。

Java中的CAS操作主要通过Unsafe类实现。Unsafe类提供了compareAndSwapInt、compareAndSwapLong、compareAndSwapObject等方法。这些方法是native方法，最终会调用处理器提供的原子指令。

CAS操作通常与自旋搭配使用。如果CAS操作失败，线程不会被挂起，而是重新获取变量的当前值，再次尝试CAS操作，直到成功。这种不断重试的机制称为自旋或忙等待。

Java的原子类如AtomicInteger、AtomicLong等都是基于CAS实现的。例如AtomicInteger的getAndIncrement方法，内部通过Unsafe的getAndAddInt方法实现，该方法使用CAS加自旋来保证原子性。

## CAS的ABA问题

ABA问题是CAS算法最常见的问题。如果一个变量V初次读取的时候是A值，准备赋值的时候检查到它仍然是A值，能说明它的值没有被其他线程修改过吗？不能，因为在这段时间它的值可能被改为其他值，然后又改回A。

ABA问题可能导致程序出现非预期的行为。例如在链表操作中，线程A读取头节点为A，准备用CAS将头节点改为A的next节点B。在执行CAS之前，线程B将头节点A删除，又插入了新的节点A，此时头节点仍然是A，但已经是不同的A对象了。线程A的CAS操作会成功，但实际上链表结构已经改变。

解决ABA问题的方案是在变量前面追加版本号或时间戳。每次变量更新时，版本号加1。CAS操作时不仅比较变量的值，还比较版本号，只有值和版本号都相等才执行更新。

Java中的AtomicStampedReference类就是用来解决ABA问题的。它内部不仅维护了对象值，还维护了一个时间戳。compareAndSet方法会同时比较预期引用和预期标志，只有两者都相等才会更新。

CAS的其他问题包括：循环时间长开销大，如果长时间CAS不成功会一直自旋，给CPU带来很大开销；只能保证一个共享变量的原子操作，对多个变量无法保证原子性，此时可以使用AtomicReference将多个变量封装成一个对象，或者使用锁。

## synchronized的用法

synchronized关键字主要有三种使用方式：修饰实例方法、修饰静态方法、修饰代码块。

修饰实例方法时，synchronized锁定的是当前对象实例。进入同步代码前要获得当前对象实例的锁。不同对象实例的synchronized方法互不影响，同一个对象实例的不同synchronized方法会互相阻塞。

修饰静态方法时，synchronized锁定的是当前类的Class对象。进入同步代码前要获得当前class的锁。静态synchronized方法和非静态synchronized方法之间不会互相阻塞，因为它们锁定的对象不同。

修饰代码块时，synchronized需要指定锁定的对象。synchronized(object)表示锁定指定对象，synchronized(类.class)表示锁定Class对象。代码块的粒度可以更细，灵活性更高。

synchronized关键字不能修饰构造方法。构造方法本身是线程安全的，因为对象还没有创建完成，不可能被多个线程同时访问。但如果构造方法中涉及共享资源的操作，需要采取适当的同步措施。

尽量不要使用synchronized(String)，因为JVM中字符串常量池具有缓存功能，相同内容的字符串字面量会指向同一个对象，可能导致意外的锁竞争。

## synchronized底层原理

synchronized同步代码块的实现使用monitorenter和monitorexit指令。monitorenter指令指向同步代码块的开始位置，monitorexit指令指向同步代码块的结束位置。

通过javap反编译字节码可以看到，synchronized代码块包含一个monitorenter指令和两个monitorexit指令。两个monitorexit是为了保证锁在正常执行和异常情况下都能被正确释放。

执行monitorenter指令时，线程试图获取对象监视器monitor的持有权。如果monitor的进入计数器为0，则线程可以获取monitor，并将计数器设为1。如果线程已经持有该monitor，则计数器加1，这就是重入的实现。如果其他线程已经持有monitor，则当前线程阻塞等待。

执行monitorexit指令时，monitor的计数器减1。如果计数器值为0，则释放monitor，其他等待的线程可以尝试获取monitor。

synchronized修饰方法时，字节码中没有monitorenter和monitorexit指令，而是使用ACC_SYNCHRONIZED访问标志。JVM通过该标志来辨别一个方法是否为同步方法，从而执行相应的同步调用。

无论是同步代码块还是同步方法，本质都是对对象监视器monitor的获取。monitor是基于操作系统的互斥锁Mutex Lock实现的，线程获取和释放monitor涉及用户态和内核态的切换，开销较大。

## synchronized锁优化

Java 6之后，synchronized引入了大量优化，包括自旋锁、适应性自旋锁、锁消除、锁粗化、偏向锁、轻量级锁等，使得synchronized的性能大幅提升。

锁的状态从低到高依次是：无锁状态、偏向锁状态、轻量级锁状态、重量级锁状态。锁可以升级但不能降级，这种策略是为了提高获得锁和释放锁的效率。

偏向锁的核心思想是：如果一个线程获得了锁，那么锁就进入偏向模式，当这个线程再次请求锁时，无需做任何同步操作，只需简单测试一下对象头的Mark Word里是否存储着指向当前线程的偏向锁。如果存在，表示线程已经获得了锁。偏向锁适用于只有一个线程访问同步代码块的场景。

轻量级锁的核心思想是：在没有多线程竞争的情况下，通过CAS操作来避免使用重量级锁。轻量级锁适用于线程交替执行同步代码块的场景，如果多个线程在同一时刻竞争锁，轻量级锁会膨胀为重量级锁。

自旋锁的核心思想是：如果持有锁的线程能在很短时间内释放锁，那么等待锁的线程就不必进入阻塞状态，只需执行忙循环等待一会儿。自旋锁避免了线程切换的开销，但如果锁被占用的时间很长，自旋会浪费CPU资源。

锁消除是指虚拟机即时编译器在运行时，对一些检测到不可能存在共享数据竞争的锁进行消除。锁粗化是指将多个连续的加锁解锁操作合并为一次锁操作，减少加锁解锁的次数。

## synchronized与ReentrantLock对比

synchronized和ReentrantLock都是可重入锁。可重入锁也叫递归锁，指的是线程可以再次获取自己的内部锁。比如一个线程获得了某个对象的锁，此时这个对象锁还没有释放，当其再次想要获取这个对象的锁时仍然可以获取。

synchronized依赖于JVM实现，ReentrantLock依赖于API实现。synchronized的优化都是在JVM层面实现的，没有直接暴露给开发者。ReentrantLock是JDK层面实现的，可以通过查看源代码了解其实现原理。

ReentrantLock比synchronized增加了一些高级功能，主要有三点：等待可中断、可实现公平锁、可以绑定多个Condition。

等待可中断是指当持有锁的线程长期不释放锁时，正在等待的线程可以选择放弃等待，改为处理其他事情。通过lock.lockInterruptibly方法实现，如果其他线程中断当前线程，当前线程会抛出InterruptedException异常。

ReentrantLock可以指定公平锁或非公锁，默认是非公平锁。公平锁是指多个线程按照申请锁的顺序来获取锁，非公平锁是指锁被释放后，后申请的线程可能先获取到锁。synchronized只能是非公平锁。

ReentrantLock可以绑定多个Condition对象，通过newCondition方法创建。不同的Condition可以实现选择性通知，而synchronized只能随机唤醒一个线程或唤醒所有线程。

性能方面，在JDK 1.6之前synchronized的性能远低于ReentrantLock。但在JDK 1.6之后，synchronized进行了大量优化，两者性能基本持平。在低竞争情况下synchronized性能可能更好，在高竞争情况下ReentrantLock的公平锁性能可能更好。
