## HashMap的底层数据结构

HashMap在JDK 1.8之前的底层数据结构是数组加链表，也就是拉链法解决哈希冲突。数组是HashMap的主体，链表则是为了解决哈希冲突而存在的。当不同的键计算出相同的数组下标时，这些键值对会以链表的形式存储在同一个数组位置。

HashMap在JDK 1.8之后的底层数据结构是数组加链表加红黑树。当链表长度大于阈值（默认为8）并且数组长度大于64时，链表会转换为红黑树，以减少搜索时间。如果数组长度小于64，则优先选择对数组进行扩容而不是转换为红黑树。

HashMap中的数组被称为table，数组中的每个元素称为一个桶。JDK 1.8中，链表节点的类型是Node，红黑树节点的类型是TreeNode，TreeNode继承自Node。

红黑树的引入解决了链表过长时查询效率低的问题。链表的查询时间复杂度是O(n)，而红黑树的查询时间复杂度是O(log n)。当哈希冲突严重导致链表很长时，红黑树能显著提升查询性能。

当红黑树的节点数量减少到6个以下时，红黑树会退化回链表。设置8和6两个不同的阈值而不是同一个值，是为了避免在阈值附近频繁地进行树化和退化转换，造成性能损耗。

## HashMap的put流程

HashMap的put操作首先会判断table数组是否为空或长度是否为0。果是，则调用resize方法进行初始化，默认初始容量为16。

接着HashMap会根据键的哈希值计算数组下标。计算方式是将扰动后的哈希值与数组长度减1进行按位与运算，即(n - 1) & hash。这个运算等价于对数组长度取模，但位运算效率更高。

如果计算出的数组下标位置为空，说明没有发生哈希冲突，直接创建一个新的Node节点放入该位置即可。

如果该位置不为空，说明发生了哈希冲突。此时先判断该位置第一个节点的哈希值和键是否与待插入的键相同。如果相同，则直接覆盖该节点的值。

如果第一个节点的键不相同，则判断该节点是否为TreeNode类型。如果是红黑树节点，则调用putTreeVal方法在红黑树中插入或更新节点。

如果是链表节点，则遍历链表。遍历过程中如果找到键相同的节点，则覆盖其值。如果遍历到链表末尾仍未找到，则在链表尾部插入新节点。JDK 1.8采用尾插法，而JDK 1.7采用头插法。

插入新节点后，如果链表长度达到树化阈值8，则尝试将链表转换为红黑树。转换前会检查数组长度是否达到64，如果不足则优先扩容。

最后，put操作会将size加1，并判断size是否超过阈值threshold。如果超过，则调用resize方法进行扩容。

## HashMap的扰动函数

HashMap的扰动函数是hash方法，它的作用是让键的哈希值更加均匀分布，减少哈希冲突的概率。

扰动函数的实现是将键的hashCode值与其自身右移16位的结果进行按位异或运算。这样做的目的是让哈希值的高16位参与到低位的运算中，因为计算数组下标时只用到了哈希值的低位。

如果不使用扰动函数，当数组长度较小时，只有哈希值的低几位参与运算，高位的信息被完全丢弃。这会导致即使两个键的哈希值高位差异很大，只要低位相同就会产生哈希冲突。

扰动函数还会处理键为null的情况。如果键为null，hash方法返回0，意味着null键总是存储在数组的第0个位置。HashMap允许一个null键和多个null值。

JDK 1.7的扰动函数进行了四次移位和异或运算，而JDK 1.8简化为一次移位和异或运算。JDK 1.8的实现虽然简单，但在性能和哈希分布之间取得了更好的平衡。

## HashMap的容量为什么是2的幂

HashMap的容量必须是2的幂，这样设计主要是为了提高计算数组下标的效率。当容量n是2的幂时，n减1的二进制表示的低位全是1，此时hash & (n - 1)等价于hash % n，但位运算的效率远高于取模运算。

如果容量不是2的幂，n减1的二进制表示中会存在为0的位。在按位与运算中，这些为0的位会导致对应的数组位置永远无法被访问到，造成数组空间的浪费和哈希分布不均匀。

HashMap的构造方法允许传入任意的初始容量，但HashMap会通过tableSizeFor方法将其向上调整为最接近的2的幂。例如传入初始容量17，实际会被调整为32。

tableSizeFor方法的实现通过一系列移位和按位或运算，将输入值的二进制表示中最高位的1之后的所有位都置为1，然后加1得到2的幂。这种实现避免了循环，效率很高。

容量是2的幂还能优化扩容时的元素迁移。JDK 1.8的扩容过程中，元素的新下标要么等于原下标，要么等于原下标加上原容量。判断依据是元素哈希值在原容量对应的那一位是0还是1，不需要重新计算哈希值。

## HashMap的负载因子与扩容

HashMap的默认负载因子是0.75。负载因子决定了HashMap的扩容时机，当HashMap中元素的数量超过容量乘以负载因子时，就会触发扩容。例如默认容量16乘以0.75等于12，当元素数量超过12时就会扩容。

负载因子设为0.75是空间和时间成本的折中。如果负载因子设置得过大，可以减少扩容次数节省空间，但哈希冲突的概率增大，会降低查询效率。如果设置得过小，哈希冲突减少查询效率提高，但会频繁扩容浪费空间。

HashMap的扩容操作通过resize方法实现。扩容时容量会变为原来的2倍，阈值threshold也会变为原来的2倍。扩容后需要重新计算所有元素的位置并迁移，这个过程称为rehash。

JDK 1.8的扩容优化：由于容量是2的幂，扩容后元素的新位置只有两种可能。如果元素哈希值在原容量对应的二进制位上是0，则新位置等于原位置。如果是1，则新位置等于原位置加上原容量。这样就避免了重新计算哈希值。

JDK 1.7在扩容时使用头插法迁移链表元素，会导致链表反转，在多线程环境下可能形成环形链表引发死循环。JDK 1.8改用尾插法，保持了链表元素的相对顺序，避免了环形链表问题，但仍然不是线程安全的。

## HashMap与HashSet的区别

HashMap实现了Map接口，用于存储键值对。HashSet实现了Set接口，用于存储对象集合。

HashSet的底层实现就是HashMap。HashSet内部维护了一个HashMap实例，将添加的元素作为HashMap的键存储，值统一使用一个名为PRESENT的静态Object对象。因此HashSet的所有操作实际上都是委托给内部的HashMap完成的。

HashMap使用put方法添加元素，需要同时传入键和值。HashSet使用add方法添加元素，只需要传入一个元素。HashSet的add方法内部调用的是map.put(element, PRESENT)。

HashMap的键不允许重复但值可以重复，HashSet中的元素不允许重复。HashSet判断元素重复的依据就是HashMap判断键重复的依据，即元素的hashCode和equals方法。

HashMap比HashSet的查询速度更快，因为HashMap通过键直接定位值。HashSet只能判断元素是否存在，无法通过一个元素获取另一个关联的数据。

## HashMap与Hashtable的区别

HashMap是非线程安全的，多线程环境下并发操作可能导致数据不一致。Hashtable是线程安全的，它的所有public方法都使用synchronized关键字修饰，同一时刻只有一个线程能访问Hashtable。

Hashtable的线程安全是通过给整个方法加锁实现的，锁的粒度很大，在高并发场景下性能很差。因此在需要线程安全的场景中，推荐使用ConcurrentHashMap而不是Hashtable。

HashMap允许存储一个null键和多个null值。Hashtable不允许键或值为null，如果存入null会抛出NullPointerException异常。

HashMap的默认初始容量是16，扩容时容量变为原来的2倍。Hashtable的默认初始容量是11，扩容时容量变为原来的2倍加1。如果指定了初始容量，HashMap会将其调整为2的幂，Hashtable则直接使用指定的容量。

HashMap在JDK 1.8之后引入了红黑树优化，当链表过长时会转换为红黑树。Hashtable始终使用数组加链表的结构，没有红黑树优化。

Hashtable是JDK 1.0就存在的遗留类，继承自Dictionary抽象类。HashMap是JDK 1.2引入的，继承自AbstractMap抽象类。Hashtable基本已被废弃，新代码中不应该使用。

## ConcurrentHashMap的底层实现

ConcurrentHashMap在JDK 1.7的底层实现是Segment数组加HashEntry数组加链表，采用分段锁机制。整个ConcurrentHashMap被分为多个Segment，每个Segment本质上是一个小的HashMap，并且Segment继承自ReentrantLock。

JDK 1.7的分段锁机制下，不同Segment的操作可以并发执行，只有操作同一个Segment时才需要竞争锁。默认的并发级别是16，意味着最多支持16个线程同时写入。Segment数组的长度一旦确定就不能改变，扩容只会扩容Segment内部的HashEntry数组。

ConcurrentHashMap在JDK 1.8的底层实现是Node数组加链表加红黑树，与HashMap的结构基本相同。JDK 1.8放弃了分段锁，改用CAS加synchronized来保证并发安全，锁的粒度细化到了数组的每个桶。

JDK 1.8的ConcurrentHashMap在put操作时，如果目标桶为空，使用CAS操作插入新节点，不需要加锁。如果目标桶不为空，则对该桶的头节点使用synchronized加锁，然后在链表或红黑树中插入节点。

JDK 1.8的ConcurrentHashMap支持多线程协同扩容。当一个线程在扩容时，其他线程如果发现正在扩容，会调用helpTransfer方法加入到扩容工作中，通过分配不同的桶区间给不同线程来并行迁移数据，提高了扩容效率。

ConcurrentHashMap使用volatile修饰Node的val字段和next指针，保证了读操作的可见性。因此get操作完全不需要加锁，性能很高。

## LinkedHashMap与TreeMap

LinkedHashMap继承自HashMap，在HashMap的基础上维护了一个贯穿所有节点的双向链表，从而保证了元素的迭代顺序。LinkedHashMap的Entry继承自HashMap的Node，并额外增加了before和after两个指针，用于维护双向链表。

LinkedHashMap支持两种迭代顺序：插入顺序和访问顺序。默认是插入顺序，即按照元素被插入的先后顺序迭代。通过构造方法传入accessOrder为true可以切换为访问顺序，即最近访问的元素会被移动到链表尾部。

LinkedHashMap的访问顺序模式可以很方便地实现LRU缓存。只需要继承LinkedHashMap并重写removeEldestEntry方法，当元素数量超过设定的容量时返回true，LinkedHashMap就会自动移除最久未使用的元素。

TreeMap基于红黑树实现，是一个有序的Map。TreeMap中的键会按照自然顺序或者构造时指定的Comparator进行排序。TreeMap的put、get、remove操作的时间复杂度都是O(log n)，相比HashMap的O(1)平均时间复杂度，TreeMap的单次操作性能较低。

TreeMap不允许键为null，因为插入时需要与其他键进行比较，null无法参与比较。但TreeMap允许值为null。选择TreeMap还是HashMap取决于是否需要排序，如果需要按键排序或范围查询，选择TreeMap，否则选择HashMap。

## CopyOnWriteArrayList

CopyOnWriteArrayList是ArrayList的线程安全版本，采用写时复制策略保证并发安全。CopyOnWriteArrayList的核心思想是：读操作不加锁，直接读取底层数组；写操作时先加锁，然后复制一份新的数组，在新数组上进行修改，最后用新数组替换旧数组。

CopyOnWriteArrayList的底层数组使用volatile修饰，保证了数组引用替换后对所有线程立即可见。因此读操作虽然不加锁，也能读取到最新的数组引用。

CopyOnWriteArrayList的写操作使用ReentrantLock加锁，保证同一时刻只有一个线程进行写操作，避免多个线程同时复制数组导致数据丢失。

CopyOnWriteArrayList的优点是读操作完全无锁，读性能非常高，并且读写可以并发执行不会互相阻塞。缺点是每次写操作都要复制整个数组，内存开销大，写性能低。此外，由于读操作可能读到旧数组，CopyOnWriteArrayList只能保证数据的最终一致性，不能保证实时一致性。

CopyOnWriteArrayList适合读多写少的并发场景，例如存储配置信息、监听器列表等。如果写操作频繁或者集合元素很多，应该考虑使用其他方案。
