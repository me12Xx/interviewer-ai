## 事务的四大特性ACID

事务的ACID特性是数据库事务必须满足的四个基本属性，分别是原子性、一致性、隔离性和持久性。

原子性Atomicity是指事务是一个不可分割的工作单位，事务中的操作要么全部完成，要么全部不完成。如果事务中的某个操作失败，整个事务都会回滚到开始前的状态，就像这个事务从未执行过一样。原子性通过undo log来实现，当事务失败或回滚时，MySQL会利用undo log中的信息将数据恢复到修改前的状态。

一致性Consistency是指事务必须使数据库从一个一致性状态变换到另一个一致性状态。一致性是指数据库的完整性约束没有被破坏，事务执行前后都是合法的数据状态。例如转账操作，A账户减少的金额必须等于B账户增加的金额，不能出现钱凭空消失或增加的情况。一致性是事务的最终目标，其他三个特性都是为了保证一致性而存在的。

隔离性Isolation是指一个事务的执行不能被其他事务干扰。即一个事务内部的操作及使用的数据对其他并发事务是隔离的，并发执行的各个事务之间不能互相干扰。隔离性通过锁机制和MVCC多版本并发控制来实现，确保事务在并发执行时能够正确地读写数据。

持久性Durability是指一个事务一旦提交，它对数据库中数据的改变就应该是永久性的，即使系统发生故障也不会丢失。持久性通过redo log来实现，当事务提交时，MySQL会先将修改写入redo log并刷新到磁盘，然后才返回提交成功，即使数据页还没有刷新到磁盘，系统崩溃后也可以通过redo log恢复数据。

## 并发事务带来的问题

在多个事务并发执行时，如果没有采取适当的隔离措施，可能会出现以下几种问题。

脏读是指一个事务读取到另一个事务未提交的数据。例如事务A修改了数据但还未提交，事务B读取了事务A修改后的数据，如果事务A回滚，那么事务B读取到的数据就是无效的脏数据。脏读会导致数据的不一致性，是最严重的问题之一。

不可重复读是指在一个事务内多次读取同一数据，但每次读取的结果不同。例如事务A第一次读取某行数据，事务B修改了该行数据并提交，事务A再次读取该行数据时发现数据已经改变。不可重复读的重点是数据的修改，同一条记录的内容发生了变化。

幻读是指在一个事务内多次查询符合条件的记录数，但每次查询的结果数量不同。例如事务A第一次查询满足条件的记录有5条，事务B插入了一条满足条件的记录并提交，事务A再次查询时发现有6条记录。幻读的重点是记录数量的变化，出现了之前不存在的记录。

不可重复读和幻读的区别在于：不可重复读是由于其他事务的UPDATE操作导致的，关注的是数据内容的变化。幻读是由于其他事务的INSERT或DELETE操作导致的，关注的是记录数量的变化。解决不可重复读的方法是行锁，解决幻读的方法是间隙锁或临键锁。

丢失修改是指两个事务同时读取同一数据并进行修改，后提交的事务会覆盖先提交的事务的修改，导致先提交的事务的修改丢失。丢失修改是最严重的问题，会导致数据完全错误。现代数据库都会通过锁机制来避免丢失修改。

## 事务的四种隔离级别

SQL标准定义了四种事务隔离级别，用于控制事务的隔离程度，隔离级别从低到高依次是：读未提交、读已提交、可重复读、串行化。

读未提交Read Uncommitted是最低的隔离级别。在该级别下，事务可以读取其他事务未提交的数据。读未提交无法解决脏读、不可重复读和幻读问题，实际应用中几乎不使用。

读已提交Read Committed级别下，事务只能读取其他事务已经提交的数据。读已提交解决了脏读问题，但无法解决不可重复读和幻读问题。读已提交是Oracle和SQL Server的默认隔离级别。

可重复读Repeatable Read级别下，在同一个事务内多次读取同一数据的结果是一致的。可重复读解决了脏读和不可重复读问题，但理论上仍可能存在幻读问题。可重复读是MySQL InnoDB存储引擎的默认隔离级别。

串行化Serializable是最高的隔离级别。在该级别下，事务串行执行，完全隔离，不会出现任何并发问题。串行化通过给每条读取的记录都加锁来实现，解决了所有并发问题，但性能最差，会导致大量的超时和锁竞争，实际应用中很少使用。

隔离级别越高，数据的一致性越好，但并发性能越差。隔离级别越低，并发性能越好,但可能出现的数据一致性问题越多。需要根据实际业务场景在性能和一致性之间做出权衡。

## MySQL的默认隔离级别

MySQL InnoDB存储引擎的默认隔离级别是可重复读Repeatable Read。可以通过SELECT @@transaction_isolation命令查看当前的隔离级别。

MySQL选择可重复读作为默认隔离级别主要是为了减少主从复制时的问题。在MySQL的binlog日志格式为STATEMENT时，如果隔离级别是读已提交，可能导致主从数据不一致。而可重复读配合binlog可以保证主从复制的数据一致性。

虽然SQL标准规定可重复读隔离级别无法完全解决幻读问题，但MySQL的InnoDB存储引擎通过MVCC多版本并发控制和临键锁机制，在可重复读隔离级别下也能够避免幻读问题。

InnoDB在可重复读隔离级别下，使用快照读可以避免幻读。快照读是指读取的是事务开始时的数据快照，即使其他事务插入了新记录，当前事务也看不到。只有当前读才可能出现幻读，但InnoDB通过临键锁锁定范围来避免幻读。

可重复读隔离级别在保证数据一致性的同时，也提供了较好的并发性能，是一个很好的平衡点。大多数场景下，MySQL的默认隔离级别可重复读已经足够使用。

## MVCC多版本并发控制

MVCC的全称是Multi-Version Concurrency Control，即多版本并发控制。MVCC是一种并发控制的方法,用于解决读写冲突，提高数据库的并发性能。

MVCC的核心思想是为每个事务提供一个数据的快照版本，事务读取的是快照版本的数据，而不是最新的数据。这样读操作不会被写操作阻塞，写操作也不会被读操作阻塞，实现了读写并发。

MVCC主要通过三个部分实现：隐藏字段、undo log版本链和ReadView读视图。

隐藏字段是指InnoDB在每行记录后面添加了三个隐藏字段。DB_TRX_ID字段记录最近修改该行记录的事务ID，DB_ROLL_PTR字段记录指向该行记录的undo log的指针，DB_ROW_ID字段是隐藏的主键，如果表没有指定主键，InnoDB会自动生成该字段。

undo log版本链是指每次修改记录时，都会将旧版本的记录写入undo log，并通过DB_ROLL_PTR指针连接起来，形成一个版本链。版本链的头部是当前最新的记录，沿着指针可以找到该行记录的所有历史版本。

ReadView读视图是事务进行快照读时生成的读视图，它决定了当前事务能看到哪些版本的数据。ReadView中包含当前活跃事务的ID列表、最小事务ID和最大事务ID等信息。

通过ReadView的可见性规则，事务可以判断版本链中的每个版本是否对当前事务可见。如果当前版本不可见，则通过DB_ROLL_PTR指针找到上一个版本，再判断可见性，直到找到可见的版本或者到达版本链的末尾。

MVCC只在读已提交和可重复读两个隔离级别下工作。读未提交总是读取最新的数据，不需要MVCC。串行化会对所有读取的记录加锁，也不使用MVCC。

## 当前读与快照读

MySQL的读操作分为当前读和快照读两种类型，它们的实现机制和可见性规则不同。

快照读又称一致性非锁定读，读取的是记录的快照版本，而不是最新版本。快照读不会给记录加锁，不会阻塞其他事务的写操作。普通的SELECT语句都是快照读，例如SELECT * FROM table WHERE条件。快照读通过MVCC实现，读取的是ReadView创建时的数据快照。

当前读读取的是记录的最新版本，并且会对读取的记录加锁，防止其他事务修改。当前读会阻塞其他事务对同一记录的修改操作。SELECT FOR UPDATE、SELECT LOCK IN SHARE MODE、UPDATE、DELETE等语句都是当前读。

在可重复读隔离级别下，快照读和当前读的行为不同。快照读在事务第一次查询时创建ReadView，之后的所有快照读都使用同一个ReadView，因此读取的数据是一致的，解决了不可重复读问题。当前读每次都读取最新的数据，不使用ReadView，如果其他事务修改了数据，当前读能看到最新的修改。

在读已提交隔离级别下，每次快照读都会创建新的ReadView，因此能看到其他事务已提交的修改，无法保证可重复读。当前读的行为与可重复读隔离级别相同，读取最新数据并加。

MVCC的快照读解决了幻读问题。在可重复读隔离级别下，事务内的所有快照读都使用同一个ReadView，即使其他事务插入了新记录，当前事务的快照读也看不到，因此不会出现幻读。但当前读可能出现幻读，需要通过临键锁来解决。

## 临键锁Next-Key Lock

临键锁Next-Key Lock是InnoDB存储引擎特有的一种锁，它是记录锁和间隙锁的组合。临键锁既锁定记录本身，也锁定记录之间的间隙，防止其他事务在间隙中插入新记录。

记录锁Record Lock锁定的是索引记录本身，防止其他事务修改或删除该记录。记录锁是最基本的行锁类型。

间隙锁Gap Lock锁定的是索引记录之间的间隙，防止其他事务在间隙中插入新记录。间隙锁不锁定记录本身，只锁定间隙范围。间隙锁的主要目的是防止幻读。

临键锁是记录锁加间隙锁，锁定一个范围，并且锁定记录本身。例如索引中有记录10、20、30，如果对20加临键锁，则锁定的范围是(10, 20]，包括20这条记录，以及10到20之间的间隙。

InnoDB在可重复读隔离级别下，对于当前读会自动加临键锁。例如SELECT * FROM table WHERE id大于10 FOR UPDATE，会锁定大于10的所有记录，以及这些记录之间的间隙，防止其他事务在这个范围内插入新记录。

临键锁解决了幻读问题。由于锁定了间隙，其他事务无法在范围内插入新记录，当前事务多次执行当前读时，查询结果的记录数量不会改变，避免了幻读。

临键锁只在可重复读隔离级别下生效。在读已提交隔离级别下，InnoDB只使用记录锁，不使用间隙锁，因此无法完全避免幻读。在串行化隔离级别下，所有读操作都会加锁，并发性能最差。

临键锁的缺点是可能锁定较大的范围，降低并发性能。例如WHERE条件是一个范围查询,会锁定整个范围，其他事务在这个范围内的插入和修改都会被阻塞。因此在设计索引和编写SQL时，应该尽量缩小锁定的范围。

## MySQL的锁分类

MySQL的锁可以从多个维度进行分类，包括锁的粒度、锁的类型和锁的模式等。

按照锁的粒度分类，可以分为表级锁、行级锁和页级锁。表级锁的粒度最大，锁定整张表，开销小但并发度低。行级锁的粒度最小，锁定单行记录，开销大但并发度高。页级锁介于两者之间，锁定一页数据。InnoDB主要使用行级锁，MyISAM使用表级锁。

按照锁的类型分类，可以分为共享锁和排他锁。共享锁Shared Lock也称为读锁，允许多个事务同时持有，但持有共享锁的事务只能读取数据，不能修改。排他锁Exclusive Lock也称为写锁，只允许一个事务持有，持有排他锁的事务可以读取和修改数据。

意向锁Intention Lock是表级锁，用于表明事务想要对表中的某些行加共享锁或排他锁。意向锁分为意向共享锁IS和意向排他锁IX。意向锁的作用是在判断是否可以对整张表加锁时，不需要逐行检查是否有行锁，只需要检查意向锁即可，提高了效率。

按照锁的算法分类，InnoDB的行锁可以分为记录锁、间隙锁和临键锁。记录锁锁定单行记录，间隙锁锁定记录之间的间隙，临键锁是两者的组合，锁定记录和间隙。

自增锁AUTO-INC Lock是一种特殊的表级锁，用于保证自增主键的连续性。当多个事务同时向包含自增列的表插入数据时，自增锁保证每个事务获取的自增值是连续的。

## InnoDB的三大日志

InnoDB存储引擎有三个重要的日志：undo log、redo log和binlog。这三个日志在事务的实现和数据恢复中起着关键作用。

undo log是回滚日志，用于实现事务的原子性。undo log记录了事务修改前的旧版本数据，当事务需要回滚时，可以利用undo log将数据恢复到修改前的状态。undo log还用于实现MVCC，通过undo log形成的版本链，事务可以读取到数据的历史版本。undo log存储在共享表空间或独立的undo表空间中。

redo log是重做日志，用于实现事务的持久性。redo log记录了事务对数据页的物理修改操作，例如在某个页的某个偏移位置写入了什么值。当事务提交时，MySQL会先将redo log写入磁盘，然后才返回提交成功，即使数据页还没有刷新到磁盘，系统崩溃后也可以通过redo log恢复数据。redo log是InnoDB特有的，是物理日志。

binlog是二进制日志，是MySQL Server层的日志，所有存储引擎都可以使用。binlog记录了所有的DDL和DML语句，以事件的形式记录，还包含了语句执行的时间等信息。binlog主要用于主从复制和数据恢复。binlog是逻辑日志，记录的是SQL语句的逻辑内容。

redo log和binlog的区别：redo log是InnoDB特有的物理日志，记录的是数据页的物理修改，是循环写的，空间固定会覆盖旧日志。binlog是MySQL Server层的逻辑日志，记录的是SQL语句的逻辑内容，是追加写的，不会覆盖旧日志。redo log用于崩溃恢复，binlog用于主从复制和数据恢复。

两阶段提交是指事务提交时，redo log和binlog的写入分为两个阶段：prepare阶段和commit阶段。prepare阶段先写入redo log并标记为prepare状态，然后写入binlog，最后再将redo log标记为commit状态。两阶段提交保证了redo log和binlog的一致性，即使在写入过程中发生崩溃，也能通过两个日志的状态来判断事务是否成功提交。

## MySQL的事务隔离实现

MySQL通过锁机制和MVCC多版本并发控制来实现不同的事务隔离级别。

读未提交隔离级别不使用任何锁机制，事务读取数据时不加锁，写数据时只加排他锁。这样其他事务可以读取未提交的数据，导致脏读问题。

读已提交隔离级别下，写操作会加排他锁直到事务结束，但读操作不加锁。InnoDB使用MVCC实现读已提交，每次快照读都创建新的ReadView，能够读取其他事务已提交的修改，因此无法保证可重复读。

可重复读隔离级别下，InnoDB通过MVCC和临键锁来实现。快照读使用MVCC，在事务第一次查询时创建ReadView并一直使用，保证了可重复读。当前读使用临键锁，锁定记录和间隙，防止其他事务在范围内插入新记录，避免了幻读。

串行化隔离级别通过给所有读操作加共享锁、写操作加排他锁来实现。所有操作都需要加锁，读写操作会相互阻塞，事务只能串行执行，完全消除了并发问题，但性能最差。

InnoDB在可重复读隔离级别下，通过MVCC解决了快照读的幻读问题，通过临键锁解决了当前读的幻读问题，这是MySQL相比其他数据库的一个重要优势。
