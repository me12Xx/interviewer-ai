## 索引的优缺点

索引的优点是能大幅提高数据检索的效率，减少查询需要扫描的数据量。索引通过创建有序的数据结构，使得数据库可以快速定位到目标数据，避免全表扫描。对于大数据量的表，索引能够将查询性能提升几个数量级。

索引还可以加速表与表之间的连接查询，特别是在实现参照完整性方面特别有意义。使用索引可以显著减少查询中分组和排序的时间，因为索引本身是有序的。

索引的缺点是会占用额外的磁盘空间。一个索引需要存储索引列的数据和指向实际数据行的指针，表越大，索引占用的空间越多。对于大型表，索引可能占用比数据本身更多的存储空间。

索引会降低数据写入的速度。当对表中的数据进行INSERT、UPDATE、DELETE操作时，不仅要修改数据本身，还要更新相关的索引。如果一个表有多个索引，每次写操作都需要更新所有相关索引，写入性能会明显下降。

索引需要维护成本。数据库需要定期对索引进行维护和优化，特别是在大量数据变动后，索引可能出现碎片，需要重建才能保持最佳性能。不合理的索引设计还可能降低查询性能，例如在选择性很低的列上建立索引。

## 索引的底层数据结构

索引常见的底层数据结构包括哈希表、B树和B+树。不同的数据结构适用于不同的查询场景，各有优缺点。

哈希表索引基于哈希函数实现，将索引列的值通过哈希函数计算得到哈希值，然后将数据存储在对应的哈希桶中。哈希索引的查询效率非常高，等值查询的时间复杂度是O(1)。但哈希索引不支持范围查询和排序，因为哈希函数破坏了数据的顺序性。哈希索引还存在哈希冲突问题，需要通过链表或其他方法解决。Memory存储引擎支持哈希索引，InnoDB和MyISAM不直接支持哈希索引。

B树是一种多路平衡查找树，每个节点可以有多个子节点。B树的所有节点都存储数据，包括内部节点和叶子节点。B树的查询、插入、删除操作的时间复杂度都是O(log n)。B树支持范围查询和排序，但由于内部节点也存储数据，相同大小的节点能存储的索引项较少，树的高度相对较高。

B+树是B树的变种，也是MySQL InnoDB存储引擎索引使用的数据结构。B+树的所有数据都存储在叶子节点，内部节点只存储索引键。B+树的叶子节点通过双向链表连接，便于范围查询。由于内部节点不存储数据，同样大小的节点可以存储更多的索引项，树的高度更低，IO次数更少，查询效率更高。

## 为什么MySQL选择B+树

MySQL的InnoDB存储引擎选择B+树作为索引结构，主要原因包括以下几点。

B+树的所有数据都存储在叶子节点，内部节点只存储索引键。这使得内部节点可以存储更多的索引项，在相同的磁盘IO次数下，B+树可以索引更多的数据。对于千万级数据量的表，B+树的高度通常只有3到4层，查询只需要3到4次IO。

B+树的叶子节点通过双向链表连接，便于范围查询和排序操作。范围查询时，只需要找到起始位置，然后顺着链表遍历即可，无需回到父节点。而B树进行范围查询时需要进行中序遍历，效率较低。

B+树的查询性能更稳定。由于所有数据都在叶子节点，所有查询都必须从根节点遍历到叶子节点，查询路径长度相同。而B树查询时，数据可能在任何节点，查询路径长度不一致，性能不稳定。

B+树更适合磁盘存储。数据库索引通常非常大，无法完全加载到内存中，需要从磁盘读取。B+树的设计使得一个节点的大小可以设置为磁盘页的大小（通常是4KB或16KB），每次IO可以读取一个完整的节点，减少了IO次数。

相比哈希索引，B+树支持范围查询、排序和前缀匹配，功能更全面。相比B树，B+树的IO效率更高，范围查询性能更好。因此B+树成为MySQL InnoDB存储引擎的首选索引结构。

## 聚簇索引与非聚簇索引

聚簇索引是指索引的顺序与数据在磁盘上的物理存储顺序相同。在聚簇索引中，数据行直接存储在索引的叶子节点中。InnoDB存储引擎的主键索引就是聚簇索引，表中的数据按照主键顺序存储。

聚簇索引的优点是范围查询和排序效率高，因为数据在物理上是连续存储的。通过聚簇索引访问数据只需要一次查询，因为叶子节点就存储了完整的数据行。聚簇索引还能减少磁盘IO，提高缓存命中率。

聚簇索引的缺点是插入速度较慢，如果插入的数据不是按主键顺序插入，可能导致页分裂，影响性能。更新聚簇索引列的代价很高，因为需要移动数据行到新的位置。一个表只能有一个聚簇索引，通常是主键。

非聚簇索引也叫二级索引或辅助索引，索引的顺序与数据的物理存储顺序无关。非聚簇索引的叶子节点存储的是索引列的值和对应的主键值，通过主键值再去聚簇索引中查找完整的数据行。

非聚簇索引的优点是一个表可以创建多个非聚簇索引，为不同的查询提供优化。插入数据时不会影响数据的物理存储顺序，不会频繁发生页分裂。

非聚簇索引的缺点是查询数据需要两次查找，先在非聚簇索引中找到主键，再根据主键在聚簇索引中找到完整数据，这个过程称为回表。回表会增加IO次数，降低查询性能。

## 回表与覆盖索引

回表是指在使用非聚簇索引查询时，先通过非聚簇索引找到主键值，然后再根据主键值到聚簇索引中查找完整的数据行。回表需要进行两次查询，增加了IO次数，降低了查询性能。

例如有一个表，主键是id，有一个非聚簇索引是name。执行查询SELECT * FROM user WHERE name等于'张三'时，首先在name索引中找到张三对应的主键id，然后根据id到聚簇索引中查找完整的数据行。如果name索引中有多条记录，每条记录都需要回表一次。

覆盖索引是指索引包含了查询所需的所有列，查询可以直接从索引中获取数据，无需回表。覆盖索引避免了回表操作，减少了IO次数，大幅提升查询性能。

使用覆盖索引的查询，在执行计划中Extra列会显示Using index，表示使用了覆盖索引。例如查询SELECT id, name FROM user WHERE name等于'张三'，如果name列上有索引，则该索引就是覆盖索引，因为查询只需要id和name，而主键id已经存储在name索引的叶子节点中。

设计索引时应该考虑覆盖索引的可能性，将常用的查询列组合成联合索引。但也要注意不要创建过多的索引，因为每个索引都需要维护成本，会降低写入性能。

## 联合索引与最左前缀原则

联合索引是指在多个列上创建的索引，例如在name和age两列上创建联合索引(name, age)。联合索引中列的顺序很重要，遵循最左前缀原则。

最左前缀原则是指联合索引可以匹配从最左边开始的连续列。对于联合索引(name, age)，可以匹配name、(name, age)，但不能单独匹配age。这是因为联合索引是先按照name排序，name相同时再按照age排序。

查询WHERE name等于'张三'可以使用联合索引(name, age)，因为匹配了最左边的name列。查询WHERE name等于'张三' AND age等于25也可以使用该索引，因为同时匹配了name和age。但查询WHERE age等于25不能使用该索引，因为没有匹配最左边的name列。

最左前缀还支持前缀匹配，例如查询WHERE name LIKE '张%'可以使用联合索引(name, age)，因为可以通过name的前缀定位到一个范围。但WHERE name LIKE '%张'不能使用索引，因为前缀不确定。

联合索引的设计原则是将选择性高的列放在前面，将常用的查询条件放在前面。选择性高是指该列的不同值越多，区分度越高。将选择性高的列放在前面，可以更快地过滤数据，减少需要扫描的行数。

联合索引可以避免创建多个单列索引。例如经常需要按name查询，也经常需要按name和age组合查询，只需要创建一个联合索引(name, age)即可，无需分别创建name索引和age索引。这样既节省了存储空间，也减少了索引维护的开销。

## 索引下推

索引下推是MySQL 5.6引入的优化技术，英文名是Index Condition Pushdown，简称ICP。索引下推的作用是在索引遍历过程中，对索引中包含的字段先做判断，过滤掉不符合条件的记录，减少回表次数。

在没有索引下推的情况下，MySQL在使用联合索引时，先根据索引的第一列定位到数据，然后回表取出完整的行记录，再判断其他列的条件是否满足。这样即使有些记录不满足条件，也需要回表，造成不必要的IO。

使用索引下推后，MySQL在索引遍历时就会检查索引中包含的其他列的条件。如果不满足条件，就不进行回表操作，直接跳过该记录。只有满足所有能在索引中判断的条件的记录，才会进行回表操作。

例如有联合索引(name, age)，查询WHERE name LIKE '张%' AND age大于20。在没有索引下推时，先根据name LIKE '张%'定位到一批记录，每条记录都回表，然后判断age是否大20。使用索引下推后，在索引遍历时就判断age是否大于20，只有同时满足name和age条件的记录才回表。

索引下推的优化效果在执行计划中，Extra列会显示Using index condition。索引下推只适用于二级索引，不适用于聚簇索引，因为聚簇索引的叶子节点就是完整的数据行，无需回表。

索引下推能够显著减少回表次数，提升查询性能，特别是在联合索引和范围查询的场景中效果明显。但索引下推只能下推索引中包含的列的条件，不在索引中的列的条件仍然需要在回表后判断。

## 唯一索引与普通索引

唯一索引要求索引列的值必须唯一，但允许有空值。唯一索引可以由一个列组成，也可以由多个列组成联合唯一索引。主键索引是一种特殊的唯一索引，不允许有空值。

普通索引是最基本的索引类型，没有唯一性的限制，允许索引列的值重复。普通索引的作用仅仅是加速查询，不对数据的唯一性做任何约束。

唯一索引和普通索引在查询性能上差异不大。查询时，普通索引找到满足条件的第一条记录后，需要继续向后查找，直到找到不满足条件的记录。唯一索引找到满足条件的记录后，由于唯一性约束，可以直接停止查找，但这个差异非常小，可以忽略。

唯一索引和普通索引在更新性能上有一定差异。当更新数据页时，如果数据页在内存中，普通索引直接更新即可。唯一索引需要判断更新后的值是否违反唯一性约束，需要将相关数据页都读入内存才能判断，增加了IO次数。

当更新的数据页不在内存中时，普通索引会将更新操作记录在change buffer中，然后就结束了。Change buffer可以合并多次更新操作，减少磁盘IO。唯一索引由于需要校验唯一性，必须将数据页读入内存，无法使用change buffer，更新性能较低。

选择唯一索引还是普通索引，主要考虑业务需求。如果业务要求某列的值必须唯一，应该使用唯一索引保证数据完整性。如果业务不要求唯一性，使用普通索引性能更好。

## 索引失效的常见场景

索引失效是指MySQL在执行SQL语句时，虽然表上有索引，但优化器选择不使用索引，而是进行全表扫描。索引失效会严重影响查询性能，应该尽量避免。

在索引列上使用函数会导致索引失效。例如WHERE YEAR(create_time)等于2023，即使create_time列有索引，也无法使用索引，因为需要对每一行都执行YEAR函数才能判断。应该改写为WHERE create_time BETWEEN '2023-01-01' AND '2023-12-31'。

在索引列上进行计算会导致索引失效。例如WHERE age加1等于26，应该改写为WHERE age等于25。

使用OR连接条件时，如果OR的任意一个条件列没有索引，则整个查询不会使用索引。例如WHERE name等于'张三' OR address等于'北京'，如果address列没有索引，即使name列有索引，也不会使用索引。

使用不等于操作符（!=或<>）可能导致索引失效。MySQL认为不等于查询的结果集可能很大，使用索引反而不如全表扫描效率高，因此选择全表扫描。

LIKE查询以通配符开头会导致索引失效。例如WHERE name LIKE '%张'无法使用索引，因为无法确定前缀。应该避免前导通配符，使用WHERE name LIKE '张%'可以使用索引。

在联合索引中，不遵守最左前缀原则会导致索引失效。对于联合索引(name, age)，查询WHERE age等于25不会使用索引，因为没有匹配最左边的列。

字符串类型的列不加引号会导致索引失效。例如WHERE name等于123，MySQL会进行类型转换，将name转换为数字与123比较，相当于对索引列使用了函数，导致索引失效。应该写成WHERE name等于'123'。

使用IS NULL可以使用索引，但IS NOT NULL可能导致索引失效，特别是当NULL值较少时，MySQL认为扫描索引不如全表扫描。

## 索引设计原则

索引设计需要综合考虑查询性能、存储空间和维护成本，遵循一些基本原则可以建立高效的索引。

为经常出现在WHERE子句、ORDER BY子句、GROUP BY子句中的列创建索引。这些列的索引可以加速查询、排序和分组操作，显著提升查询性能。

选择区分度高的列建立索引。区分度是指列中不同值的数量占总行数的比例，区分度越高，索引的效果越好。例如性别列只有男女两个值，区分度很低，不适合建立索引。

尽量使用短小的索引。对于字符串类型的列，可以创建前缀索引，只索引字符串的前几个字符。前缀索引可以减少索引占用的空间，提高索引的效率，但要选择合适的前缀长度，保证区分度。

优先考虑创建联合索引而不是多个单列索引。联合索引可以覆盖多个查询场景，减少索引的数量，节省存储空间和维护成本。设计联合索引时，将选择性高的列放在前面，将常用的查询条件放在前面。

避免创建冗余索引和重复索引。例如已经有联合索引(name, age)，就不需要再创建单独的name索引，因为联合索引可以覆盖对name列的查询。重复索引是指在相同的列上创建多个相同类型的索引，没有任何意义。

控制索引的数量，不要创建过多的索引。每个索引都需要占用存储空间，并且在进行INSERT、UPDATE、DELETE操作时需要更新索引，过多的索引会降低写入性能。一般建议一个表的索引数量不超过5个。

考虑使用覆盖索引减少回表。对于经常查询的列，可以将它们组合成联合索引，这样查询就可以直接从索引中获取所有需要的数据，无需回表，提升查询性能。

定期分析和维护索引。使用EXPLAIN分析SQL语句的执行计划，检查索引是否被正确使用。使用SHOW INDEX查看索引的统计信息，删除不再使用的索引。对于数据变化频繁的表，定期使用OPTIMIZE TABLE优化表和索引，减少碎片。
